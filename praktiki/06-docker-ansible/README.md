# Практическая работа. Docker и Ansible

Курс «Защита ПО автоматизированных систем», разбор на занятии у Чертоганова К.А. Отдельного PDF с номером у этой работы нет. На паре шли от ручных команд на сервере к файлам: Infrastructure as Code, Docker Compose, DNS внутри Docker, healthcheck, Ansible и SSH-туннель.

Я собрал стенд файлами. `docker compose up`, прогон плейбука и `run-ansible-in-docker.sh` на этой машине не запускал: образы качать и пакеты ставить для сдачи файлов не нужно. Готовой таблицы `docker compose ps` поэтому нет. Ниже команды, которыми это проверяется, и что в них смотреть.

## Цель

Сделать одно приложение из двух контейнеров так, чтобы его можно было поднять повторно с того же файла, без набора команд руками на VPS. Nginx открыт для проверки на порту 8080. Postgres с хоста не публикуется, frontend ждёт, пока база реально принимает подключения. Установка Docker и запуск того же compose лежат в плейбуке для Ubuntu.

## Ход работы

Структура как на слайде 1.2, плюс `ansible.cfg` и скрипт запуска Ansible из контейнера:

```
infrastructure-lab/
  ansible/inventory.ini
  ansible/playbook.yml
  ansible/ansible.cfg
  app/compose.yml
  run-ansible-in-docker.sh
```

### Compose

Файл `infrastructure-lab/app/compose.yml`. Имя файла именно `compose.yml`, как на слайдах 2.2 и 5.2.

Два сервиса. `database` — образ `postgres:16`, пользователь, пароль и база `demo`, healthcheck `pg_isready -U demo -d demo` каждые 5 секунд, таймаут 5 секунд, 5 попыток. Порта 5432 в файле нет: снаружи хоста база не торчит, другой контейнер ходит к ней по имени `database` в сети Compose. `frontend` — `nginx:alpine`, наружу опубликован `8080:80`. `depends_on` с `condition: service_healthy` держит nginx, пока проверка базы не станет успешной.

Сначала мне казалось, что хватит обычного `depends_on`: база «запущена», можно стартовать фронт. На занятии как раз разбирали, что процесс PostgreSQL уже есть, а соединения он ещё не принимает. Поэтому в файле не просто порядок запуска, а healthcheck.

Пароль `demo` стоит в `compose.yml`, потому что так было на слайде: без `POSTGRES_USER`, `POSTGRES_PASSWORD` и `POSTGRES_DB` этот пример не поднимается. Для локальной лабы так и оставил. В репозиторий такой пароль класть нельзя, если это уже не учебный стенд. Даже простой пароль из презентации потом остаётся в истории git. Других паролей в файлах нет.

Проверки со слайдов. Рабочий каталог — `infrastructure-lab/app`. Вывода команд у меня нет, я их не выполнял.


У `database` в статусе жду `healthy`. У `frontend` в колонке портов должен быть `8080`, у `database` опубликованного порта быть не должно. Саму таблицу `ps` сюда не вставляю.

Имя контейнера базы на слайде `app-database-1`: проект называется по каталогу `app`, сервис `database`, один экземпляр. Я этот контейнер не смотрел. Если в `docker compose ps` имя другое, в `inspect` подставляю его.

Ручная проверка выше идёт из каталога `app`, имя проекта будет `app`. Плейбук копирует тот же файл в `/opt/infrastructure-lab` и запускает его уже оттуда, имя проекта тогда другое. Это один и тот же compose, два разных места запуска.

### Ansible

Плейбук для Ubuntu, файл `infrastructure-lab/ansible/playbook.yml`. Хосты — группа `servers`.

`inventory.ini`:

```
[servers]
localhost ansible_connection=local
```

Чужой живой адрес я не писал. Внизу закомментирован пример `vps ansible_host=203.0.113.10 ansible_user=ubuntu`. Это документационная сеть, не настоящий сервер.

В `ansible.cfg` указан `inventory = inventory.ini`. Строка `host_key_checking = False` закомментирована и не действует. На учебной ВМ её иногда выключают, чтобы Ansible не ждал «yes» при первом SSH. На рабочем контуре ключ хоста проверяют: иначе можно подключиться не к той машине и отдать туда плейбук. Я проверку не отключал.

Плейбук с `become: true`, потому что пакеты и каталог `/opt` ставятся от root. Задачи такие:

1. `ansible.builtin.apt`: пакеты `docker.io` и `docker-compose-v2`, `state: present`. Это пакеты из репозитория Ubuntu, не скрипт установки Docker, скачанный через curl.
2. `ansible.builtin.service`: служба `docker`, `state: started`, `enabled: true`.
3. Каталог `/opt/infrastructure-lab`, иначе копировать файл некуда.
4. Копия `app/compose.yml` в `/opt/infrastructure-lab/compose.yml`.
5. `ansible.builtin.command`: `docker compose -f /opt/infrastructure-lab/compose.yml up -d`.

`changed_when: false` я не ставил. Иначе Ansible показывал бы «без изменений» даже когда контейнер только что создался. У `command` нет своей проверки состояния, он каждый раз выполняет строку. Я смотрю вывод: если есть `Started` или `Created`, задача изменённая. Docker Compose пишет эти слова в stderr, поэтому проверяю и stdout, и stderr. Если контейнеры уже есть и в выводе только то, что они Running, этих подстрок нет, и изменение не засчитывается.

Повторный прогон я не делал и чужой лог сюда не подставляю. По самим задачам второй запуск не переустанавливает Docker. `apt` с `state: present` ставит пакет только когда его нет: `docker.io` и `docker-compose-v2` уже стоят — установка заново не нужна. `service` со `state: started` и `enabled: true` не перезапускает службу, если она уже запущена и включена. `copy` не переписывает файл, если содержимое то же. Команда `docker compose up -d` на втором прогоне всё равно выполняется, Compose сам смотрит текущие контейнеры. Для Ansible это не «изменение», пока в выводе нет `Started` или `Created`. В этом и есть идемпотентность этого плейбука: один файл можно применить ещё раз, хост не ставят с нуля.

Проверка плейбука на Ubuntu, из каталога `infrastructure-lab/ansible`. Сначала один раз, потом тот же файл ещё раз:

```
ansible-playbook -i inventory.ini playbook.yml
ansible-playbook -i inventory.ini playbook.yml
```

На второй раз пакеты Docker заново ставиться не должны. Я этот прогон здесь не выполнял.

### Ansible из контейнера

Скрипт `infrastructure-lab/run-ansible-in-docker.sh`. Я его не запускал и образ не качал.

Его запускают из `infrastructure-lab`. Имя образа лежит в `ANSIBLE_IMAGE`, по умолчанию `ansible-image` — локальный тег, как на слайде, не адрес реестра. Скрипт делает `docker run`, монтирует текущий каталог в `/ansible`, внутри выполняет `ansible all -m ping` (рабочий каталог в контейнере — `/ansible/ansible`, там inventory и `ansible.cfg`), затем `docker stop` и `docker rm`. `sleep infinity` в `docker run` только держит контейнер живым: иначе короткий процесс образа сразу кончается и `exec` не к чему подключать.

```
./run-ansible-in-docker.sh
```

Перед этим тег `ansible-image` уже должен быть на машине. Скрипт сам ничего не скачивает, но голый `docker run` по несуществующему имени полезет в реестр, поэтому я его и не стартовал.

### SSH-туннель

Отдельный скрипт на чужой сервер я не делал. Ниже схема с занятия. В `compose.yml` порт оставлен как на слайде 2.2, `"8080:80"`, чтобы проверка `curl http://localhost:8080` шла с той машины, где запущен стенд.

Если nginx стоит на VPS и должен слушаться только с самого сервера, публикацию на все адреса заменяют привязкой к localhost. Фрагмент для этого варианта, в файл я его не вставлял:

```yaml
# ports:
#   - "127.0.0.1:8080:80"
```

Тогда на сервере страница есть на `127.0.0.1:8080`, с чужого адреса этот порт не открывается. Со своего ноутбука держу туннель, сессию не закрываю, пока смотрю сайт:

```
ssh -L 3000:127.0.0.1:8080 ubuntu@SERVER
```

`SERVER` здесь обозначение машины из условия, не чей-то адрес. Браузер на ноутбуке открывает `http://localhost:3000`. SSH забирает этот трафик и на сервере отдаёт его в `127.0.0.1:8080`, где слушает nginx.

Снаружи остаётся SSH, вход по ключу. Страница открывается уже из этой сессии. Порт 8080 на всех интерфейсах принял бы запрос от любого, кто видит хост, без неё.

## Мини-тест

1. Руками команды на VPS не набираю, потому что они остаются в истории терминала у одного человека. Сервер пересоздали — список шагов надо вспоминать, легко пропустить пакет или порт, у соседа получится другая машина. В файлах те же шаги лежат в репозитории, их видно и можно применить ещё раз.

2. Несколько контейнеров одной командой поднимает Docker Compose. `docker compose up -d` читает `compose.yml` и запускает сервисы из него, а не отдельным `docker run` на каждый.

3. Контейнер frontend находит базу по имени `database`. Compose собирает общую сеть и свой DNS: имя сервиса указывает на текущий адрес контейнера. После `docker compose restart database` имя то же, IP может стать другим. Поэтому в настройках имя сервиса.

4. Healthcheck нужен, чтобы дождаться готовности сервиса. «Процесс запущен» значит только то, что основной процесс контейнера жив. Postgres в этот момент ещё может не принимать SQL, и nginx уже полезет в базу. `pg_isready -U demo -d demo` как раз проверяет, что база отвечает. Пока статус не `healthy`, frontend с `condition: service_healthy` не стартует.

5. Повторный запуск плейбука ещё раз приводит хост к тому же состоянию. Docker второй раз не ставится, если `docker.io` и `docker-compose-v2` уже есть: у задачи `apt` стоит `state: present`. Служба не дёргается заново, если она запущена. Это и есть идемпотентность на этом плейбуке.

6. SSH-туннель нужен, когда сервис слушает только localhost на сервере. С интернета до `127.0.0.1:8080` не достучаться, это как раз защита. `ssh -L 3000:127.0.0.1:8080 ubuntu@SERVER` открывает порт 3000 у меня и через уже установленную SSH-сессию доходит до nginx на сервере. Порт приложения в интернет для этого открывать не надо.

## Вывод

Стенд описан файлами, а не списком команд, которые надо помнить. `compose.yml` поднимает nginx и Postgres одной командой, 5432 наружу не публикует, frontend ждёт healthcheck базы, а не просто старта процесса. Имя `database` в сети Docker переживает смену IP, поэтому адрес в конфиг не зашит. Плейбук ставит `docker.io` и `docker-compose-v2` из репозитория Ubuntu и запускает тот же compose; второй прогон не должен ставить Docker заново. На VPS страницу логичнее открывать туннелем на localhost, чем слушать 8080 на всех интерфейсах.

Прогон `docker compose ps`, `curl` и плейбука я не делал, готового вывода этих команд в отчёте нет.
