# Практическая работа № 1. Git: ветки, слияние, удалённый репозиторий

Дисциплина: Защита ПО автоматизированных систем.

## Цель

Отработать обычный цикл: ветка под задачу, коммит, слияние в `main`, отдельный конфликт и отправка в удалённый репозиторий. Проект лежит в этой папке, история коммитов — в корне репозитория `studydevops2026`.

`README.md` здесь специально короткий: по заданию после разрешения конфликта в нём остаётся заголовок `# Super Project v2.0`. Сам отчёт вынесен сюда, чтобы не затирать этот файл.

## Что лежит в проекте

- `main.py` — приветствие с именем
- `README.md` — заголовок проекта
- `docs/info.txt` — пустой, как в методичке
- `config.ini` — из самостоятельной части
- `git-history.txt` — вывод `git log`, чтобы не искать хеши заново

## Ход работы

Репозиторий инициализировал с веткой `main`.

Стартовый набор: `main.py` с `Hello, World!`, `README.md` с заголовком `# Project Name`, пустой `docs/info.txt`.

```
git add .
git commit -m "feat: initial project structure added"
```

Дальше ветка под приветствие:

```
git checkout -b feature/add_greeting
```

В `main.py` функция стала принимать имя, вызов внизу — `main("Student")`.

```
git add main.py
git commit -m "feat: add personalized greeting function"
git checkout main
git merge feature/add_greeting
git branch -d feature/add_greeting
```

Расхождения с `main` не было, поэтому слияние прошло fast-forward. Отдельного merge-коммита на этом шаге нет, это как раз видно на графе.

### Конфликт

Две ветки поменяли одну и ту же строку.

```
git checkout -b hotfix/readme_update
```

В ветке заголовок заменил на `# Super Project v2.0`, коммит `docs: update title`.

Вернулся в `main` и там поставил `# Super Project v1.9`, коммит `docs: fix version`.

```
git merge hotfix/readme_update
```

Git остановился на конфликте в `README.md`. Маркеры убрал, оставил `# Super Project v2.0`.

```
git add README.md
git commit -m "merge: resolve conflict in README"
```

Ветку `hotfix/readme_update` после слияния удалил.

## Ответы на контрольные вопросы

1. `git merge` склеивает истории и может оставить merge-коммит. `git rebase` переписывает коммиты ветки поверх другой, история получается линейной, хеши коммитов меняются. Уже отправленные в общую ветку коммиты rebase-ом лучше не трогать.

2. `--no-ff` заставляет создать merge-коммит, даже если можно просто перемотать указатель. Без него при fast-forward ветка в графе пропадает: остаётся прямая линия, и не видно, что изменения приехали отдельной веткой. На приветствии так и вышло, на `config.ini` merge-коммит остался специально.

3. `rejected (non-fast-forward)` значит, что на сервере есть коммиты, которых нет локально. Нельзя затирать их через `--force` в `main`. Сначала `git fetch`, потом `git pull` (merge или rebase), разобрать конфликты, если они есть, и только после этого `git push`.

4. Индекс — это снимок, который попадёт в следующий коммит. Рабочая папка и коммит — разные вещи. `git add` кладёт в индекс выбранные изменения. Даже если файл уже отслеживается, без `git add` в коммит уйдёт старая версия из индекса, а не то, что сейчас в редакторе. Так можно закоммитить только часть правок.

5. Несохранённые в индекс правки убираются через `git restore файл` (раньше то же делали `git checkout -- файл`). Файл возвращается к версии из индекса.

6. Что изменено, но ещё не в индексе: `git status` и подробнее `git diff`. Уже добавленное в индекс смотрит `git diff --cached`.
