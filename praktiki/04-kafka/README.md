## Цель

Собрать обмен сообщениями между двумя сервисами на FastAPI через Apache Kafka. Кластер из одного брокера, рядом Kafka UI. Топики `orders` (3 партиции) и `notifications` (1 партиция). Продюсер на порту 8000 принимает HTTP и пишет в брокер, консьюмер на порту 8001 читает и отдаёт накопленное по HTTP.

Дальше по заданию: топик `errors`, параллельная обработка сообщений, HAProxy перед брокером и RabbitMQ, чтобы сравнить очередь с логом Kafka.

## Ход работы

### Два listener

В методичке у брокера один listener: `PLAINTEXT://localhost:9092`, и этот порт опубликован на хост. Для uvicorn на Windows адрес верный. Для Kafka UI нет.

UI сидит в другом контейнере, в его bootstrap я указываю `kafka:9092`. Первое соединение по docker-сети до брокера доходит: порт внутри контейнера слушается. Дальше брокер в ответе metadata отдаёт не тот адрес, куда клиент подключился, а `advertised.listeners`. В методичке там `localhost:9092`. Контейнер UI воспринимает localhost как себя, брокера по этому имени нет, и кластер в интерфейсе отваливается уже после bootstrap.

Я развёл два listener, протокол у обоих PLAINTEXT:

- `INTERNAL`, бинд `0.0.0.0:9092`, наружу рекламируется `kafka:9092`. Сюда ходят kafka-ui, HAProxy и kafka-init. На хост 9092 не публикую.
- `EXTERNAL`, бинд `0.0.0.0:9094`, наружу рекламируется `localhost:9094`. Этот порт проброшен на Windows, сюда смотрит uvicorn.

`KAFKA_INTER_BROKER_LISTENER_NAME=INTERNAL`: единственный брокер ходит к себе по внутреннему имени, а не через localhost хоста. Имена listener прописаны в `KAFKA_LISTENER_SECURITY_PROTOCOL_MAP`, без карты Kafka такие имена не принимает.

Брокер один, поэтому `KAFKA_OFFSETS_TOPIC_REPLICATION_FACTOR`, `KAFKA_TRANSACTION_STATE_LOG_MIN_ISR` и `KAFKA_TRANSACTION_STATE_LOG_REPLICATION_FACTOR` стоят в 1. Если поставить больше, служебный топик некому реплицировать, брокер не становится рабочим. Автосоздание топиков выключено: иначе консьюмер, стартовавший раньше init, создаст `orders` с одной партицией, а `--if-not-exists` число партиций уже не изменит.

### Топики через kafka-init

В методичке топики создаются руками: `docker exec -it kafka bash` и `kafka-topics --create`. После каждого пересоздания контейнера это надо повторять, а в каталоге работы не остаётся, с какими параметрами их создавали.

Я сделал сервис `kafka-init` на том же образе `confluentinc/cp-kafka:7.6.1`. Свой entrypoint у него заменён на `bash /init/create-topics.sh`. Скрипт ждёт, пока `kafka-topics --list` на `kafka:9092` начнёт отвечать, потом создаёт топики, если их ещё нет:

- `orders`, 3 партиции, replication factor 1
- `notifications`, 1 партиция, replication factor 1
- `errors`, 1 партиция, replication factor 1 (это уже самостоятельное задание)

Bootstrap внутри сети именно `kafka:9092`, не `localhost:9094`: init — контейнер, ему нужен INTERNAL. Повторный запуск не падает на «topic already exists» из-за `--if-not-exists`. В конце скрипт печатает `describe`, по логу видно число партиций.

### Продюсер

`producer_service/main.py`, порт 8000. В методичке клиент создаётся в `lifespan` и ходит на `localhost:9092`, тело заказа кладётся через `order.dict()`. На pydantic v2 метода `.dict()` нет, я пишу `model_dump(mode="json")`. Адрес брокера беру из `KAFKA_BOOTSTRAP`, по умолчанию `localhost:9094`.

Эндпоинты:

- `POST /orders/` — `order_id`, `user_id`, `product`, `quantity`, топик `orders`
- `POST /notify/` — `user_id`, `message`, топик `notifications`
- `POST /errors/` — `code`, `message`, топик `errors`
- `GET /health`

Если брокера нет, процесс не падает. Ошибка соединения печатается в консоль uvicorn, клиенту уходит 503 и короткий `detail`, без traceback. Когда брокер появится, следующий POST подключается сам, uvicorn из-за этого перезапускать не нужно. Пока живого клиента нет, `/health` отвечает `degraded` и показывает bootstrap. Неверный JSON — это 422 от FastAPI, к брокеру такой запрос не доходит.

### Консьюмер

`consumer_service/main.py`, порт 8001. Три консьюмера, у каждого свой `group_id`: `orders-group`, `notifications-group`, `errors-group`. Автокоммит выключен. Если у группы ещё нет offset, читаю с начала топика (`auto_offset_reset=earliest`), иначе сообщения, отправленные до старта uvicorn, в список не попадут.

На каждое нормальное сообщение вешаю `asyncio.create_task`. Внутри задачи `await asyncio.sleep(1)`, потом запись в список. Списки и копирование для GET закрыты `asyncio.Lock`: список трогают и фоновые задачи, и HTTP. `GET /orders/`, `GET /notifications/`, `GET /errors/` отдают копию списка и `count`.

Сразу после POST список ещё пустой: задача спит секунду. Имеет смысл подождать чуть больше секунды. Несколько сообщений подряд не складываются в несколько секунд, задачи стартуют сразу и спят параллельно. Это параллельность внутри одного процесса. Число консьюмеров в группе от неё не растёт: процесс один, все партиции `orders` назначены ему.

Offset коммичу после того, как сообщение уже лежит в списке. Если более поздний offset той же партиции обработался раньше (его sleep закончился первым), коммит этого offset я откладываю, пока не закроется дырка с начала. Иначе брокер счёл бы раннее сообщение обработанным, хотя оно ещё в sleep. Сам `consumer.commit` вызывает только цикл чтения: aiokafka нельзя дёргать из задачи обработки, пока тот же объект ждёт следующее сообщение. Задача после `sleep` только помечает offset готовым, а цикл забирает отметку и коммитит. Код этого — `OffsetTracker` в `consumer_service/main.py`.

Список живёт в памяти процесса. После перезапуска uvicorn он пустой, в топике сообщения при этом остаются. Если offset уже закоммичен, заново в список они не приедут, их смотреть в Kafka UI. Чтобы группа прочитала топик с начала, ей нужен другой `group_id` или сброс сохранённого offset.

### Проверка

Запросы из PowerShell. `curl` в PowerShell — это алиас `Invoke-WebRequest`, поэтому вызываю `curl.exe`. Слэш в конце пути нужен: так эндпоинты объявлены.

Заказ:

```powershell

```

Ожидаю `{"status":"success","message":"Order 1 sent to Kafka"}`.

Уведомление:

```powershell
curl.exe -s -X POST http://localhost:8000/notify/ -H "Content-Type: application/json" --data-raw '{"user_id":100,"message":"Your order has been processed"}'
```

Ожидаю `{"status":"success","message":"Notification sent to user 100"}`.

Через секунду с лишним:

```powershell
curl.exe -s http://localhost:8001/orders/
curl.exe -s http://localhost:8001/notifications/
```

В ответе список и `count`. В Kafka UI тот же заказ лежит в топике `orders` на вкладке Messages, даже после того как консьюмер его прочитал.

Ошибка (самостоятельное задание):


Здоровье сервисов: `curl.exe -s http://localhost:8000/health` и то же на порту 8001. При живом брокере `status` равен `healthy`.

### HAProxy

Конфиг `haproxy/haproxy.cfg`, сервис в том же `docker-compose.yml`, образ `haproxy:2.9`, порт `9093:9093`. Режим TCP: фронт `bind *:9093`, бэкенд `server kafka1 kafka:9092 check`, баланс `roundrobin`. Второй сервер закомментирован, это образец на тот случай, когда появится ещё один брокер.

Строку `log /dev/log` из методички я не копировал. В официальном образе нет сокета syslog, с ней HAProxy сразу завершается. `daemon` тоже не ставил: контейнеру нужно, чтобы процесс остался на переднем плане. Адрес бэкенда `kafka:9092`, не `localhost:9092`: прокси в сети compose, localhost внутри его контейнера — это он сам. `9092` здесь — INTERNAL listener.

Продюсер по умолчанию на HAProxy не идёт. Рабочий адрес — `localhost:9094`.

Если хочется именно постучаться в прокси, в том окне, где uvicorn:

```powershell
$env:KAFKA_BOOTSTRAP = "localhost:9093"
python -m uvicorn main:app --port 8000
```

Обратно на брокер:

```powershell
$env:KAFKA_BOOTSTRAP = "localhost:9094"
```

То же самое можно выставить консьюмеру, переменная одна. Первое TCP-соединение при этом придёт на HAProxy, и он прокинет его на `kafka:9092`. Дальше клиент Kafka берёт адреса из metadata, из `advertised.listeners` того listener, который принял соединение на стороне брокера. HAProxy открыл INTERNAL, в ответе будет `kafka:9092`. С Windows это имя не резолвится, и следующие соединения уже не через 9093.

Пока в кластере один брокер и он рекламирует свой адрес, один HAProxy перед ним не становится балансировкой. `roundrobin` при одном живом сервере просто всегда выбирает его. Чтобы трафик оставался на прокси, брокеры должны рекламировать адрес прокси, и их должно быть несколько. Для лабы конфиг лежит в репозитории и поднимается вместе с кластером.

Таймауты в конфиге как в методичке: connect 5 с, клиент и сервер по 50 с. На короткую проверку этого хватает.

## Самостоятельные задания

### 1. Топик errors

Топик создаёт `kafka-init`: 1 партиция, replication factor 1. В продюсере `POST /errors/` с полями `code` и `message`. В консьюмере третья группа `errors-group` и `GET /errors/` со списком и `count`. Пример curl выше.

### 2. Параллельная обработка

На каждое сообщение своя задача: `asyncio.create_task`, внутри `await asyncio.sleep(1)`, затем запись в список. Списки закрыты `asyncio.Lock`, наружу GET отдаёт копию под тем же локом.

Это не добавляет участников в consumer group. Группа по-прежнему одна на топик, процесс один. Партиции делятся между процессами с одним `group_id`, а задачи только не дают секундной паузе встать в очередь друг за другом.

### 3. RabbitMQ

Сервис `rabbitmq` в том же compose: образ `rabbitmq:3-management`, порты 5672 и 15672. Логин и пароль берутся из `RABBITMQ_USER` и `RABBITMQ_PASSWORD`, если их нет — `guest` / `guest`. Так только на своём ноутбуке. На хосте, который доступен не мне одному, guest оставлять нельзя: перед `docker compose up` задаю нормального пользователя и пароль, и те же переменные в окне, где запускаю скрипты. Уже созданный контейнер старого пользователя не забывает, его надо пересоздать (`docker compose rm -sf rabbitmq`, потом снова `up -d`).

В обычной установке RabbitMQ пользователь guest пускает только с localhost. В официальном docker-образе для лабы это ограничение снято, иначе с Windows до опубликованного 5672 было бы не подключиться.

Скрипты в `rabbitmq_demo/`, клиент `aio-pika`, очередь `orders`. Это не топик Kafka, имя просто то же.

```powershell
cd rabbitmq_demo
python -m pip install -r requirements.txt
python consumer_rmq.py
```

Во втором окне:

```powershell
python producer_rmq.py
```

Продюсер объявляет очередь и публикует JSON заказа. Свой JSON можно передать аргументом. Консьюмер читает, печатает и подтверждает через `message.process()`: без исключения сообщение ack, из очереди оно уходит. Пароль в лог скрипты не пишут. Веб-интерфейс: http://localhost:15672 .

Сравнение без секундомера. В Kafka сообщение остаётся в логе, его читает каждая группа со своего offset. `orders-group` его забрала, в топике оно всё равно лежит, другая группа могла бы прочитать то же самое. В RabbitMQ это очередь: сообщение забирает консьюмер, после ack в очереди его нет. Второго получателя у той же копии уже не будет, для рассылки нужен exchange и отдельные очереди.

Одно сообщение на localhost я не засекал и не буду объявлять, кто быстрее. Консьюмер Kafka в этой работе ещё и спит секунду на обработке, так что часы брокеров здесь ничего не решают. Сравнивать есть что хранится и кто это видит.

## Контрольные вопросы

### 1. Kafka и RabbitMQ

Kafka — лог. Сообщение пишется в партицию и лежит, пока не истечёт срок хранения. Сколько угодно групп читают его независимо, у каждой свой offset. RabbitMQ в этом задании — очередь: сообщение доставляется консьюмеру и после ack из очереди исчезает. Если читателей несколько на одну очередь, они делят сообщения, а не получают копию каждый.

Kafka уместна, когда одно и то же событие нужно нескольким независимым сервисам или когда историю надо перечитать. Заказ, уведомление и разбор ошибок у меня как раз три независимых чтения, поэтому это топики. RabbitMQ уместен, когда работу надо сделать один раз и убрать из очереди: письмо, файл, разовая джоба. Очередь `orders` в `rabbitmq_demo` как раз про это. Выбор у меня от того, должно ли сообщение пережить чтение.

### 2. Зачем несколько партиций

Партиция — кусок топика, который одна группа читает параллельно. Внутри группы на партицию приходится не больше одного активного консьюмера. У `orders` три партиции, значит в `orders-group` можно параллельно читать тремя процессами. У `notifications` и `errors` по одной, там группа читает одним потоком, сколько процессов ни поставь.

Порядок сообщений есть только внутри партиции. По всему топику его нет. Партиций больше, чем консьюмеров, — лишние просто висят на тех же процессах, зато читателя можно добавить позже без нового топика. Уменьшить число партиций у уже созданного топика нельзя, поэтому `kafka-init` задаёт его сразу, а автосоздание я выключил. Свой один процесс консьюмера все три партиции `orders` держит сам. Задачи со `sleep(1)` этот потолок не поднимают.

### 3. Consumer groups

Группа — это общий `group_id`. Брокер делит партиции топика между её участниками. Если я подниму второго консьюмера с тем же `orders-group`, партиции `orders` разъедутся между двумя процессами, одно сообщение обработает только один из них. Уйдёт процесс — будет rebalance, его партиции заберут оставшиеся.

Другой `group_id` — другая группа, свой offset, те же сообщения она получит ещё раз. Поэтому уведомления не забирают заказы: у меня три группы на три топика, `orders-group`, `notifications-group` и `errors-group`. Они не конкурируют друг с другом.

### 4. HAProxy

В этой работе HAProxy — TCP-прокси перед брокером. Слушает 9093, соединение отдаёт на `kafka:9092`, алгоритм `roundrobin`. Для TCP ещё обычны `leastconn` (сервер, у которого меньше активных соединений) и `source` (один и тот же адрес клиента закрепляется за одним сервером). При одном бэкенде чередовать нечего, второй сервер в конфиге закомментирован как образец.

Роль балансировщика он выполнит, когда брокеров несколько и клиенты продолжают ходить в прокси. Клиент Kafka после первого ответа переходит на адреса из metadata. Пока брокер рекламирует себя, прокси остаётся только на первом соединении. Подробнее я расписал в разделе про HAProxy: как выставить `KAFKA_BOOTSTRAP=localhost:9093` и почему ответ metadata уводит клиент на `kafka:9092`.

### 5. Гарантии доставки

По умолчанию у такого консьюмера at-least-once: offset коммитится после обработки. Упадёт процесс после записи в список, но до commit — сообщение придёт ещё раз, в списке будет дубль. Закоммитить до обработки и упасть на `sleep` — сообщение потеряется, это ближе к at-most-once. Поэтому автокоммит я выключил. Отметку «обработано» задача ставит после `append`, а commit делает цикл чтения, когда по партиции нет дырки в offset.

Exactly-once в Kafka делается идемпотентным продюсером и транзакциями, когда чтение, обработка и запись чужого топика проходят одной транзакцией. Это не флаг «включить и забыть», отдельно тут не разворачиваю.

### 6. Что смотреть в Kafka UI

http://localhost:8080 . Смотрю, что брокер жив, что топики `orders`, `notifications` и `errors` есть и у `orders` три партиции. На вкладке Messages — тела, которые послал продюсер. В группах — их offset и lag: если lag растёт, консьюмер не читает или не успевает. После перезапуска uvicorn список в памяти пустой, а сообщения в топике на месте, это как раз видно здесь.

### 7. Почему aiokafka, а не kafka-python

FastAPI обслуживает запросы на одном event loop. `aiokafka` асинхронный: пока брокер отвечает, цикл может принять другой запрос, тот же `/health`. `kafka-python` синхронный. Его `send` блокирует воркер до ответа брокера, и остальные запросы этого процесса стоят вместе с ним. Для сервиса на FastAPI это плохая связка, поэтому в requirements стоит `aiokafka`.

### 8. Если брокер лежит

Продюсер не роняет процесс и не отдаёт клиенту traceback. В консоли uvicorn остаётся тип и текст исключения. `POST /orders/`, `/notify/` и `/errors/` отвечают 503 с понятным `detail`: брокер недоступен или запись не принята. `GET /health` при этом отвечает, `status` будет `degraded`, пока нет живого клиента. Следующий POST пробует подключиться снова. Консьюмер в такой ситуации тоже не валит HTTP: списки пустые, `/health` — `degraded`, пока не перезапустишь uvicorn уже после брокера.

## Вывод

Стенд из методички у меня поднимается одним `docker compose up -d`: Zookeeper, один брокер, Kafka UI, создание топиков, HAProxy и RabbitMQ. Продюсер и консьюмер живут на хосте и ходят в Kafka по `localhost:9094`, потому что адрес для контейнеров и адрес для Windows — разные listener. HAProxy в этой конфигурации не балансирует нагрузку, конфиг всё равно в репозитории и стартует вместе с кластером, как просит задание. RabbitMQ рядом, чтобы на одном ноутбуке увидеть разницу лога и очереди. Засекать, кто быстрее доставит одно сообщение, я не стал: на localhost это ничего не показывает.
