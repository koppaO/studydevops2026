# Практика 4. Kafka, HAProxy, RabbitMQ

## Что сделал

Всё поднимается из `docker-compose.yml`: Zookeeper, Kafka, Kafka UI на порту 8080, HAProxy на 9093, RabbitMQ на 5672 и 15672.

У брокера два адреса. Контейнеры ходят на `kafka:9092`. Uvicorn на Windows — на `localhost:9094`. Один `localhost:9092` в advertised UI из контейнера не открывает: для него localhost это он сам.

Топики создаёт `kafka-init`: `orders` на 3 партиции, `notifications` и `errors` по одной. Скрипт ждёт, пока брокер ответит.

Продюсер, порт 8000:

```
cd producer_service
pip install -r requirements.txt
uvicorn main:app --port 8000
```

`POST /orders/`, `POST /notify/`, `POST /errors/`. Если брокер недоступен, ответ 503.

Консьюмер, порт 8001, три группы: `orders-group`, `notifications-group`, `errors-group`. На каждое сообщение своя задача и `sleep(1)`, потом запись в список. Списки под lock. `GET /orders/`, `/notifications/`, `/errors/` отдают список и count.

Offset пишу после обработки и только если по партиции нет дырки. Commit делает цикл чтения, не задача со sleep: у aiokafka один consumer нельзя дёргать из двух задач сразу.

HAProxy в `haproxy/haproxy.cfg`, режим tcp, roundrobin, бэкенд `kafka:9092`. Строку `log /dev/log` не ставил, в образе из-за неё процесс падает. Клиент после первого ответа всё равно берёт адрес из metadata, поэтому при одном брокере прокси нагрузку не делит. Конфиг в репозитории есть, продюсер по умолчанию ходит на `localhost:9094`.

RabbitMQ: `rabbitmq_demo/producer_rmq.py` и `consumer_rmq.py`, очередь `orders`. Логин guest только для локальной машины. Кто быстрее доставит одно сообщение, не замерял: на localhost разницы не видно, а консьюмер Kafka ещё и спит секунду.

Пример заказа:

```
curl -X POST http://localhost:8000/orders/ -H "Content-Type: application/json" -d "{\"order_id\":1,\"user_id\":100,\"product\":\"Laptop\",\"quantity\":1}"
```

Потом `curl http://localhost:8001/orders/`.

## Вопросы

1. Kafka хранит лог, сообщение читают разные группы. RabbitMQ — очередь, сообщение забирает консьюмер. Лог удобен, когда одни и те же события нужны нескольким сервисам. Очередь — когда задачу надо отдать одному.
2. Несколько партиций дают параллельное чтение. Внутри группы на партицию один активный консьюмер.
3. Группа делит партиции между своими консьюмерами и помнит свой offset. Другая группа читает то же самое отдельно.
4. HAProxy здесь TCP-прокси. Алгоритм roundrobin. Ещё бывают leastconn и source. При одном брокере чередовать нечего.
5. По умолчанию at-least-once: offset после обработки. Упадёт до commit — сообщение придёт ещё раз. Exactly-once надо собирать отдельно, транзакциями и идемпотентным продюсером.
6. В Kafka UI смотрю топики, партиции и сами сообщения.
7. aiokafka не блокирует event loop FastAPI. Обычный kafka-python на await-ах стоит.
8. Если брокер недоступен, продюсер отвечает 503 и пишет причину в лог, клиенту traceback не отдаю.

## Вывод

Поднял брокер, UI и три топика. Продюсер принимает HTTP и кладёт JSON в Kafka, консьюмер читает с паузой в секунду. HAProxy в файле есть, но при одном брокере это не балансировка. RabbitMQ рядом, чтобы было с чем сравнить очередь и лог.
