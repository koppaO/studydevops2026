Настроить автоматический контроль качества для Python-проекта. Тесты пишу на pytest, внешний вид кода выравнивает black, импорты раскладывает isort, стиль и явные ошибки смотрит flake8. Хуки pre-commit гоняют это при коммите. Те же flake8 и pytest стоят в CI, чтобы проверка не оставалась только на моей машине.

## Приложение

Код в `src/main.py`. У приложения заголовок «QA Demo». Модель `Item` — два поля: `name` (str) и `price` (float). Товары храню в словаре `items_db` в памяти процесса.

Маршруты:

- `GET /` — `200` и `{"message": "Hello, QA!"}`.
- `POST /items/` — создаёт товар, `201` и текст `Item <имя> created`. Повтор того же имени — `400` и `Item already exists`.
- `GET /items/{name}` — товар по имени. Если имени нет — `404` и `Item not found`.
- `GET /items/` — список всех товаров.
- `DELETE /items/{name}` — самостоятельное задание 1. Первый запрос удаляет товар и отвечает `200` с текстом `Item <имя> deleted`. Повторный DELETE того же имени и DELETE имени, которого не было, отвечают `404` и `Item not found`.

Пустой `src/__init__.py` нужен, чтобы `src` был пакетом и тест мог сделать `from src.main import app`.

## Тесты и общая память

Тесты лежат в `tests/test_main.py`. Запросы идут через `TestClient`, отдельный сервер для них не нужен.

В методичке шесть тестов сидят на одном `items_db` и ждут, что предыдущий тест уже положил туда Laptop. `test_create_duplicate_item` сразу ждёт 400, `test_get_item` сразу читает `/items/Laptop`. Пока pytest идёт сверху вниз по файлу, цепочка сходится. Один `test_get_item` или другой порядок сбора — словарь пустой либо в нём другие имена, и тест падает. Проверяется остаток от соседа, а не сам эндпоинт.

В `tests/conftest.py` фикстура `clear_items_db` с `autouse=True`. Pytest вызывает её сам: перед тестом `items_db.clear()`, после теста ещё раз. Каждый тест начинает с пустого словаря, поэтому его можно запускать отдельно.

Данные тест готовит внутри себя:

- дубликат: первый `POST` ждёт 201, второй с тем же JSON ждёт 400 и `Item already exists`;
- чтение товара: сначала создание Laptop, потом `GET /items/Laptop`;
- список: внутри теста создаются Laptop и Mouse, в ответе словарь имён и цен;
- удаление: создание, DELETE с 200 и сообщением `Item Laptop deleted`, проверка что `GET` уже 404, затем тот же DELETE ещё раз — снова 404. Отдельный `test_delete_non_existent_item` бьёт в имя, которого не создавали.

Самостоятельное задание 3. `test_create_item` переписан через `@pytest.mark.parametrize` на три товара: Laptop 999.99, Mouse 25.5, Keyboard 79.0. Pytest запускает эту функцию три раза, по разу на пару «имя, цена». После POST тест читает товар обратно и сверяет оба поля: иначе цена в параметрах ни на что бы не влияла.

В выводе `pytest -v` получается 10 кейсов: три из них — варианты `test_create_item`, остальные семь функций по одному разу.

`tests/fixtures/sample.json` содержит товар Laptop за 999.99. Приложение и тесты этот файл не открывают. Он лежит, чтобы хуку `check-json` было что разобрать: без единого json в дереве хук отрабатывает вхолостую и не видно, смотрит ли он файлы.

## Конфиги

`pyproject.toml`.

- black: длина строки 88, `target-version` — py310. В методичке написано `target-version = ['py310']`. TOML одинарные кавычки не принимает, я поставил двойные, иначе файл не разбирается.
- isort: профиль `black`, длина 88, `multi_line_output = 3`. Добавил `known_first_party = ["src"]`, чтобы импорт `src.main` стоял отдельным блоком, а не вперемешку с fastapi и pytest.
- pytest: каталог `tests`, файлы `test_*.py`, функции `test_*`, `addopts = "-v --tb=short"`. В `pythonpath` указал `["."]`: pytest поднимает корень проекта в `sys.path` и находит пакет `src` без `pip install -e .`.

`.flake8`: длина 88, `extend-ignore = E203, W503`, исключения `.git`, `__pycache__`, `build`, `dist`, `.venv`, `venv`. E203 и W503 отключены, потому что black сам ставит пробел перед `:` в срезе и переносит строку перед оператором. С включёнными кодами flake8 ругался бы на уже отформатированный файл.

`.pre-commit-config.yaml`:

- pre-commit-hooks v4.5.0: `end-of-file-fixer`, `check-added-large-files`, `trailing-whitespace` и `check-json` (задание 2);
- black 24.3.0;
- isort 5.13.2 (в примере методички он уже был, я его оставил);
- flake8 7.0.0.

Один раз в клоне хук вешается в `.git/hooks`:

```powershell
pre-commit install
```

Проверка всего дерева, не только индекса:

```powershell
pre-commit run --all-files
```

`pre-commit install` только записывает хук в `.git/hooks` и пакеты проекта не ставит. Окружения хуков по `rev` из конфига скачиваются с GitHub при первом `pre-commit run --all-files` или при первом `git commit`, поэтому версии в конфиге указаны явно.

## Как запускать

Из корня этого каталога, с включённым окружением:

```powershell
pytest
pytest tests/test_main.py::test_root
pytest -k "delete or duplicate"
pytest --cov=src --cov-report=html

```

`pytest` без аргументов читает `pyproject.toml`: ищет тесты в `tests`, печатает имена (`-v`) и короткий traceback (`--tb=short`).

Покрытие считает pytest-cov. HTML ложится в `htmlcov/index.html`. На Windows открываю так:

```powershell
start htmlcov/index.html
```

В отчёте видно, какие строки `src/main.py` тесты не задели. Каталог `htmlcov` — результат прогона, в репозиторий я его не кладу.

## Black и flake8

black переписывает файл: кавычки, пробелы, переносы, пустые строки между функциями. После него код выглядит одинаково, независимо от того, кто его правил.

Так выглядит кусок до black:

```python
def ping( ):
    msg={'message':'Hello, QA!'}
    return msg
```

После `black`:

```python
def ping():
    msg = {"message": "Hello, QA!"}
    return msg
```

flake8 файл не трогает. Он печатает код и номер строки. Ошибку, которую нельзя поправить автоматом, приходится убирать руками, иначе хук flake8 останавливает коммит.

Строка, которую flake8 ловит, а black оставляет (в код проекта я её не вставлял):

```python
import os


def ping():
    return "ok"
```

Имя `os` нигде не используется. black такой импорт не выкидывает: он ровняет вид файла и не решает, нужен ли модуль. flake8 пишет `F401 'os' imported but unused`.

Поэтому они стоят парой. black убирает разнобой в оформлении. flake8 после этого всё ещё видит мёртвый импорт, неизвестное имя и другие ошибки в уже «красивом» файле. В конфиге pre-commit black идёт раньше flake8: сначала файл приводится к формату, потом линтер смотрит результат.

## Ответы на контрольные вопросы

### 1. Как запустить один тест или группу

Один тест — по пути до функции:

```powershell
pytest tests/test_main.py::test_root
```

У параметризованного теста в выводе `-v` есть суффикс набора, например `test_create_item[Laptop-999.99]`. Его можно передать так же, через `::`.

Группа по части имени:

```powershell
pytest -k delete
```

`-k` принимает выражение: `pytest -k "delete or duplicate"`. Весь файл: `pytest tests/test_main.py`.

Маркер вешается декоратором `@pytest.mark.slow`, запуск — `pytest -m slow`. Свой маркер лучше объявить в `pyproject.toml` в списке `markers`, иначе pytest пишет предупреждение о неизвестном маркере. В этой работе отдельных маркеров нет: отбор закрывают `::`, `-k` и parametrize.

### 2. Зачем TestClient вместо живого HTTP

`TestClient` передаёт запрос в ASGI-приложение внутри процесса. Порт не занимается, uvicorn для тестов не нужен, от сети и свободного порта 8000 прогон не зависит. Статус и JSON приходят из того же `app`, который описан в `src/main.py`. Исключение в эндпоинте pytest показывает обычным traceback.

Сервер, таймауты и прокси этот клиент не покрывает. Для проверки маршрутов и кодов ответа этого хватает, и такой прогон нормально живёт в CI.

У свежей Starlette импорт `TestClient` может предупредить, что вместо `httpx` рассчитан пакет `httpx2`. На статусы тестов предупреждение не влияет. В `requirements.txt` оставил `httpx`: так написано в методичке.

### 3. Black и flake8, почему вместе

black — форматер. Он меняет файл и приводит его к одному виду. Смысл программы он не проверяет.

flake8 — линтер. Файл он не переписывает, а сообщает о нарушениях: неиспользованный импорт (`F401`), неизвестное имя, слишком длинная строка, если она не свернулась при форматировании.

Вместе они закрывают разные дыры. black снимает споры о пробелах и кавычках. flake8 ловит то, что после выравнивания всё ещё ошибка. Пример с `import os` выше как раз такой: файл уже в стиле black, а линтер всё равно ругается. В pre-commit black стоит раньше flake8. Если black поправил файл, коммит прерывается: правку нужно снова добавить в индекс.

### 4. Что делает pre-commit на git commit

`pre-commit install` записывает вызов фреймворка в `.git/hooks/pre-commit`. На `git commit` git запускает этот хук до того, как коммит создан. Фреймворк читает `.pre-commit-config.yaml` и гоняет хуки по файлам, которые лежат в индексе.

Часть хуков правит файлы сама: `end-of-file-fixer`, `trailing-whitespace`, black, isort. Если файл изменился, коммит не создаётся. В индексе и на диске разный текст, нужно снова сделать `git add` и повторить коммит. `flake8` и `check-json` файл не чинят: ненулевой код выхода, и коммит тоже не проходит.

Так в историю не попадает битый JSON и код, который не проходит стиль. Проверка стоит рядом с коммитом, а не только на сервере CI. Без коммита то же самое запускается командой `pre-commit run --all-files`.

### 5. Что такое coverage и почему 100% не гарантия

Покрытие — доля строк (или ветвей) `src`, которые выполнились, пока шли тесты. Считаю так:

```powershell
pytest --cov=src --cov-report=html
```

pytest-cov отмечает пройденные строки `src` и кладёт отчёт в `htmlcov/`.

100% означает, что каждая посчитанная строка хотя бы раз выполнилась. Верность программы из этого не следует. Строка `return {"message": f"Item {name} deleted"}` станет покрытой, даже если тест не сверит текст и не проверит, что имени больше нет в `items_db`. Ветка `if name not in items_db` не выполняется тестом, который удаляет только существующий товар: процент может быть высоким, а ответ 404 никто не смотрел. Поэтому рядом с отчётом у меня отдельные проверки на успешное удаление и на отсутствующее имя. Процент показывает, куда тесты ещё не заходили.

### 6. Почему pyproject.toml

`pyproject.toml` — общий файл настроек Python-проекта, его описывает PEP 518. black, isort и pytest находят его сами. Настройки этих трёх инструментов лежат в одном месте, отдельные `pytest.ini` и `.isort.cfg` для этой работы не нужны.

flake8 7 из коробки `pyproject.toml` не читает. Его настройки остались в `.flake8`, как в методичке. По двум файлам видно и стиль, и то, на что линтер закрывает глаза (E203, W503).

### 7. Как вставить это в CI

Тот же прогон, что локально, только на GitHub. Файл workflow: [.github/workflows/qa.yml](../../.github/workflows/qa.yml).

Он запускается на `push` и на `pull_request`. Секретов в файле нет. Шаги такие: checkout репозитория, Python 3.11, `pip install -r requirements.txt`, затем `flake8` и `pytest`. Если линтер или тест падает, проверка красная, это видно до слияния ветки.

GitHub Actions читает workflows только из `.github/workflows` в корне репозитория. Поэтому файл лежит там, а не рядом с практикой. У шагов `working-directory: praktiki/05-qa`, иначе пайплайн не найдёт `requirements.txt` и `pyproject.toml`.

## Вывод

Собрал FastAPI-приложение «QA Demo»: модель `Item`, память `items_db`, маршруты из методички и `DELETE /items/{name}`. Тесты ходят через `TestClient`. Фикстура `clear_items_db` с `autouse=True` очищает словарь перед каждым тестом, поэтому прогон одного теста и другой порядок больше не зависят от остатков в `items_db`.
